## Genuine problems found

### 1. `analyze` misses its main pipeline calls (CONFIRMED)
Source `analyze()` calls `_execute_parse`, `_resolve_scip`, `build_graph`,
`detect_noise_files`, `enforce_graph_size` directly. Cartog's trace shows none
of these from the `analyze` function node — it jumps to `finalize`,
`write_text`, etc. The target functions exist as nodes and ARE resolved from
other callers (`build` calls `_execute_parse`/`_resolve_scip`/`build_graph`/
`detect_noise_files`; `map` and `parse` too), but `analyze` uses tuple-unpacking
assignment (`target_path, stage_dir, ... = _execute_parse(...)`) which the
SCIP/structural resolver does not attribute to the enclosing function. Real
accuracy gap.

### 2. False channel nodes (CONFIRMED)
15 `channel` nodes include obvious false positives from ordinary string args:
`target`, `imports`, `patterns`, `documents`, `symbols`, `arguments`, `source`,
`decorator`, `config_warnings`, `torture_py_graph` (a test fixture name),
`*.py`, `/`, `*`, `ws://localhost`. These come from the generic MQ binding
rule that treats any `X("string", ...)` call as a channel binding when X is
not a builtin. On the torture repos the strings happened to be channel names;
on real code they are ordinary call arguments. This is a real accuracy bug
that makes the graph noisy for LLM input.

### 3. `query` command missing (CONFIRMED)
Cartog has no `cartog/cli/commands/query.py` — that command exists only in the
torture sample. The `query` command in the plan was never implemented in
cartog itself. Not a cartog bug — a plan/sample mismatch.

## Conclusion
9 of 10 CLI command flows match source exactly. One (analyze) needs a focused
follow-up. A confirmed false-positive channel problem exists and should be
fixed before trusting graph output for LLM consumption.
